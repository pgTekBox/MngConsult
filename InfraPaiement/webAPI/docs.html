API 60secPaiement

Intégrez les paiements EFT (encaissements clients et décaissements fournisseurs) dans votre application SaaS.

URL de base

# Version canonique
https://<votre-hôte>/api/v1

Les appels sans /v1 (ex. /api/balance) restent acceptés pour rétro-compatibilité mais renvoient l'en-tête X-Api-Deprecation. Chaque réponse porte X-Api-Version.

Authentification

Chaque requête doit inclure votre clé d'API dans l'en-tête X-Api-Key (ou Authorization: Bearer <clé>). Les clés sont générées par la plateforme et isolent automatiquement vos données.

curl https://votre-hôte/api/v1/balance \
  -H "X-Api-Key: sk_live_..."

Deux types de clés

Clé abonné (sk_…) — accède aux ressources de votre propre compte.

Clé partenaire (pk_…, Modèle B) — provisionne des abonnés via /abonnes et agit au nom de l'un d'eux en ajoutant l'en-tête X-Abonne-Id: <id> sur les ressources scopées.

# Agir au nom d'un abonné avec une clé partenaire
curl https://votre-hôte/api/v1/balance \
  -H "X-Api-Key: pk_live_..." \
  -H "X-Abonne-Id: 42"

Conventions

Montants

Tous les montants sont en cents entiers (ex. 10000 = 100,00 $), devise CAD.

Idempotence

Pour les créations (encaissements, décaissements), envoyez un en-tête Idempotency-Key unique : un rejeu renverra le même objet sans doublon.

Pagination

Les listes acceptent ?limit= (défaut 25, max 100) et ?offset=. La réponse contient un bloc pagination :

{ "data": [ ... ],
  "pagination": { "limit":25, "offset":0, "count":25, "has_more":true, "next_offset":25 } }

Limite de débit

Par clé d'API. En-têtes X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset. Au dépassement : statut 429 + Retry-After.

Erreurs

Format uniforme : { "error": { "code": "...", "message": "..." } }. Codes HTTP : 400 (validation/règle métier), 401 (clé), 404, 429, 500.

Webhooks

Configurez une URL de notification (côté plateforme). Nous envoyons un POST JSON signé à chaque transition :

En-têteValeur
X-Webhook-Eventpayment.initiated · payment.settled · payment.returned · payout.initiated · payout.settled · payout.returned
X-Webhook-Signaturesha256=HMAC-SHA256(secret, corps)
X-Webhook-Delivery-Ididentifiant de livraison

Vérifiez la signature en recalculant le HMAC-SHA256 du corps brut avec votre secret, puis comparez à X-Webhook-Signature.

// Node.js — vérification
const sig = "sha256=" + crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
if (sig === req.headers["x-webhook-signature"]) { /* authentique */ }

Partenaires (Modèle B)

Réservé aux clés partenaire (pk_…). Un partenaire (canal de revente) provisionne et gère ses propres abonnés (locataires), puis agit en leur nom via l'en-tête X-Abonne-Id.

MéthodeCheminDescription
GET/abonnesLister les abonnés provisionnés (paginé, ?search=)
POST/abonnesProvisionner — corps { legal_name*, display_name, business_number, email, city, province, postal_code }
GET/abonnes/{id}Obtenir un abonné
POST/abonnes/{id}/kybLancer une vérification KYB (met à jour kyb_status)
GET/abonnes/{id}/kybHistorique des vérifications KYB

Agir au nom d'un abonné

Pour les ressources scopées (/balance, /clients, /fournisseurs, /payments, /payouts, /webhook), ajoutez l'en-tête X-Abonne-Id avec l'identifiant d'un abonné vous appartenant :

# 1) Provisionner un abonné
curl -X POST https://votre-hôte/api/v1/abonnes \
  -H "X-Api-Key: pk_live_..." -H "Content-Type: application/json" \
  -d '{ "legal_name": "Boulangerie Tremblay inc.", "business_number": "1234567890" }'
# => { "id": 42, "kyb_status": "NonDebute", ... }

# 2) Créer un client POUR cet abonné (auth déléguée)
curl -X POST https://votre-hôte/api/v1/clients \
  -H "X-Api-Key: pk_live_..." -H "X-Abonne-Id: 42" \
  -H "Content-Type: application/json" \
  -d '{ "name": "Client du boulanger" }'

Sans X-Abonne-Id, une clé partenaire reçoit 400 sur les ressources scopées. Un X-Abonne-Id pointant un abonné non rattaché au partenaire renvoie 403.
